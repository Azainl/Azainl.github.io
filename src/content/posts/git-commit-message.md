提交信息写得好不好，代码能说明吗？不能。

代码只告诉你"发生了什么"，提交信息才告诉你"为什么这么做"。而"为什么"，正是几个月后回看时最想知道的。

## 别让提交信息成为"废案"

最没有价值的提交信息大概长这样：

```
git commit -m "update"
```

它既没说明改了什么，也没说明为什么改。半年后翻日志，这条提交对理解历史毫无帮助。

我不是说每条都要长篇大论，而是至少要能回答一个问题：**这次改动解决了什么**。

## 我常用的前缀约定

一套简单的 `<类型>: <简述>` 结构，一眼就能扫出这次改动的性质：

- `feat:` 新功能
- `fix:` 修 bug
- `perf:` 性能优化
- `refactor:` 重构，不改变行为
- `docs:` 改文档/注释
- `chore:` 杂务，构建、依赖等

```bash
git commit -m "feat: 首页列表按年份分组"
git commit -m "fix: 返回按钮在文章页错位"
git commit -m "docs: 更新操作文档的返回说明"
```

这套约定不花哨，但足够让 `git log --oneline` 变成一张可读的改动清单。

## 主体部分留着力气

改动能用一个短句说清楚时，就只写标题。需要展开时，空一行写主体，说明"为什么"，而不是"做了什么"：

```text
fix: 返回后滚动位置丢失

之前翻页时用 history.replaceState(null) 把 state 清空，
导致 Astro 无法从 history.state 恢复滚动。改为保留 state
并写入滚动位置。
```

读这段的人会先看到结论，需要时再深挖原因。

## 一个判断标准

> 半年后的你读这条信息，能不能不打开代码就明白改了什么、为什么改？

能，就合格。不能，就补两句。

提交信息本质上是写给未来的自己看的注释，多花十秒钟，省下的可能是一下午的考古时间。
