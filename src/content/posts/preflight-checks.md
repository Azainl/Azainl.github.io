每次改完东西，从"我觉得改好了"到真的按下发布，中间有一段很容易被忽略的时间。以前我靠记忆逐项确认：首页看了吗、深色模式看了吗、链接点得开吗。结果是——一定会漏。

## 靠记忆检查，等于没检查

人对自己刚改过的地方印象最深，也恰恰最容易忽略"没改的地方有没有被连带影响"。改一次样式，往往只盯着那个组件看，忘了它在窄屏下是另一副样子。

清单能解决一部分问题，但清单也要靠人执行，而人总有赶时间的时候。

## 能写成断言的，就别写进清单

后来我把这些检查逐条写成了断言，放进一个脚本：

```powershell
npm run check
```

它用无头 Chrome 打开真实页面，检查有没有横向溢出、字体有没有加载、深浅主题切换是否生效、导航有没有换行、全站内部链接是否都可达、订阅源是否正常。现在有一百多条，跑一遍两分钟左右。

关键在于：**断言给的是结论，不是印象**。"首页看起来没问题"和"134 条全部通过"，是两种完全不同的确定性。

## 检查脚本自己也会骗你

这里有个更隐蔽的坑：我的检查脚本一开始**无论有没有失败，退出码都是 0**。

意思是它明明报了 `FAIL`，但只要我不逐行读完输出，或者只看最后几行，就完全看不出来。有六个失败就这样被忽略了很久——脚本"跑过了"，问题却还在。

修法很简单：结尾统计失败数，有失败就返回非 0 的退出码。**一个不会失败的检查，等于没有检查。**

## 让机器跑，但别挡住发布

有了断言，自然会想放进 CI，每次推送都跑一遍。但我没有把它设成发布门禁——检查依赖浏览器，偶发失败是常事，一旦卡住，明明没问题的改动也发不出去。

所以我把它和部署拆成了两个工作流：一个负责检查和构建，一个负责部署。检查失败会红，能立刻看到；但部署该走的还走。等这条链稳一段时间，再考虑要不要合并。

## 写在最后

把检查交给脚本，省下的不只是时间，更是那种"我是不是漏了什么"的不安。剩下的精力，可以真正花在内容上。

> 能自动确认的事，不要留在脑子里过夜。
