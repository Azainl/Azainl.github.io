以前做响应式，断点永远挂在视口宽度上。`@media (min-width: 768px)` 说的是"屏幕够宽"，可同一张卡片，放在正文里和放在侧边栏里，明明空间差很多，却只能套同一套规则。容器查询把这件事纠正了过来：组件按**自己容器**的宽度来决定怎么排。

## 之前的别扭

一个文章卡片，宽的时候左图右文、窄的时候上下堆叠。问题是它可能被放在三栏布局里，也可能被放在全宽列表里。用媒体查询，我只能在"视口宽"和"视口窄"之间二选一，没法表达"容器窄就堆叠"。

于是只能用各种 `hack`：给不同位置传不同的 `class`、用 CSS 变量手动覆盖……越绕越乱。

## 容器查询怎么做

思路分两步：先声明"这个元素是容器"，再在子元素里用 `@container` 查询这个容器的尺寸。

```css
/* 声明容器：以行内尺寸作为查询基准 */
.card-wrapper {
  container-type: inline-size;
}

/* 子元素按容器宽度响应，而不是视口 */
.card {
  display: grid;
  grid-template-columns: 1fr;
  gap: 0.75rem;
}

@container (min-width: 420px) {
  .card {
    grid-template-columns: 120px 1fr;
    gap: 1.25rem;
  }
}
```

关键在于 `@container` 看的是 `.card-wrapper` 的宽度，不是屏幕宽度。同一个卡片，塞进窄侧栏就自动堆叠，放进宽列表就自动左右排——不需要任何额外 class。

## 它解决的到底是什么

媒体查询回答的是"设备是什么样"，容器查询回答的是"这块地方有多大"。后者更贴近组件该有的样子：**组件只该关心自己被给了多少空间**。

我把博客里几处"因为放的位置不同而要写两套样式"的卡片都换成了容器查询，代码一下短了，也不再依赖"这个组件会被放在哪"的假设。

## 一点提醒

- `container-type: inline-size` 只认行内尺寸（宽度），够用了；要连高度也查，用 `size`，但会触发尺寸 `containment`，留意子元素高度塌陷。
- 容器查询的浏览器支持已经很成熟，现代项目可以放心用，不用再挂 `polyfill`。

组件真正"独立"的标志，是它不关心自己身在何处，只关心手头这点空间。容器查询让这件事第一次变得自然。
