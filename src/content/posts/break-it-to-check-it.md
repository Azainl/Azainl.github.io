写完一批检查脚本，跑一遍，全绿。

按理说该收工了。但我盯着那几百行 "passed" 看了一会儿，冒出一个不太舒服的念头：**这些检查是因为代码对，还是因为它们本来就不会喊？**

## 绿灯只证明了一件事

一条断言通过，能证明的只有"现在的代码满足这条断言"。它不能证明这条断言在代码坏掉时会失败。

这两种情况差别很大。一个写错的断言——比较了错误的两个量、取错了元素、把条件写反——永远会通过，而且看起来和真正有效的断言一模一样。

我没法靠读代码分辨。只能改坏，看反应。

## 做法：备份、改坏、重建、跑、恢复

流程很笨，但可靠：把要动的源文件备份到临时目录，手动改坏**一处**，重新构建，跑全部检查记下哪几条红了，再从备份恢复、复跑一遍确认回到全绿。

四组故障，故意选的是"像真 bug"的改法，而不是语法错误——写错语法构建当场就挂，那是另一层防线，测不到断言本身。

| 改坏的地方 | 期望的结果 |
| --- | --- |
| 去掉左侧留白列，改成两列 | 关于三列结构和居中的断言红 |
| 容器宽度改回全站宽 | 关于正文列宽度的断言红 |
| 目录的列号从 3 改成 2 | 只有"目录在右栏"那条红 |
| 宽屏下目录 sticky 改成 fixed | 同上，只有那一条红 |

结果和预期一致：10 条断言分别转红，恢复之后回到 446 条全绿。

一次只改一处。同时改两处，红了也不知道是谁的功劳，这一轮就白做了。

## 中间踩的坑

前三组全部报 "PATTERN NOT FOUND"——脚本根本没改到目标文件。

原因很土：那些 CSS 是 CRLF 换行，而我用多行字符串做匹配，字符串里是纯 `\n`，永远匹配不上。改成"按行号定位 + 校验该行原文"之后才注入成功。

这个坑顺手也提醒了一件事：**检查脚本自己也是代码，也会坏，而且坏起来悄无声息。**

## 顺手发现的真问题

改坏的过程中发现，图片尺寸插件里还写着一个 576px 的硬编码上限，而它对应的 CSS 规则早就改掉了。两处不同步，构建不会报错，只是桌面端会白下一倍体积的图。

这种问题不在任何断言的覆盖范围内。修掉它，然后给它补一条。

> 测试全绿有两种可能：代码是对的，或者测试睡着了。

## 写在最后

改坏再恢复，一轮下来要重跑四次构建、四次检查，花掉的时间够写半篇文章。

但这是唯一能回答"我到底有没有防线"的办法。别的时候，我看到的都只是绿灯。

**没被改坏过的断言，和被删掉的断言，可靠性是一样的。**
