一篇文章写得再好，如果分享出去的链接只是光秃秃一行字，点开的人总要少一些。那张预览图（`og:image`）不参与阅读，却决定了别人愿不愿意点。

## 一张图要满足的条件

社交平台对这张图有几个硬要求：尺寸最好 1200×630，格式得是 PNG 或 JPEG，而且**不能是 SVG**。最后一条就是我踩的第一个坑。

## 坑一：用 SVG 当分享图

站点的图标和分享图我原本都放的是 SVG——矢量、体积小、改起来方便，看起来是个聪明的选择。

问题是没有哪份文档提醒过我：Facebook、Twitter、LinkedIn 这些平台**都不解析 SVG 作为预览图**。结果就是每次分享出去，别人看到的都是一个没有图的卡片，而我本地看一切正常。

判断方法很简单：把链接丢进平台自带的分享调试工具，那张图的位置是空的，就说明没生效。

## 坑二：在构建时生成

既然一张图不够（每篇文章标题都不一样），那就在构建时按标题生成。听起来很合理，我写完脚本，CI 上渲染出来的却全是方框——**构建机器上没有中文字体**。

本地 Windows 有系统字库，一切正常；GitHub Actions 的构建机器是干净的 Linux 环境，默认不带中文，于是标题里的汉字全变成了豆腐块。

## 我的做法：预生成，然后提交进仓库

最后换了个思路：不在构建时生成，而是**写一个脚本在本地把图渲染好，直接提交进仓库**。

```powershell
npm run og
```

它会为每篇文章生成 1200×630 的 PNG，放进 `public/og/`，并写一份清单记下哪些文章有专属分享图。构建时只是把这些静态文件原样发出去——CI 不需要字体，也不需要额外的图像库。

代价是改了标题要记得重跑一次。所以我给运行时加了兜底：清单里没有的文章回退到全站默认图，漏跑最多退化成一张通用卡片，不会出现裂图。

## 写在最后

这件事我改了两次方向，最后落在"把不确定性挪到本地"上。构建环境是你控制不了的，能提前算出来的东西，就别留到构建时再算。

> 分享图不参与阅读，但它决定了有没有人读得到。
