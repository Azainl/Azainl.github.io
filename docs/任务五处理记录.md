## P1-4.3 🔴 断链检查（本轮唯一真缺陷）

- **问题**：`check.mjs:787` 那段的标题写「**全站**内部链接检查」，但实现是：开一个 tab 导航到 `BASE + '/'`（首页），抓 `a[href]` 里 `startsWith('/')` 的链接，去重后逐个 fetch。**只扫了首页。**
- **排查**（实测数量差）：
  - 首页去重站内链接 **29–33 条**；
  - 把 sitemap 里全部页面（54 页）的 HTML 合起来去重 → **60 条**站内链接。
  - → **约 27 条站内链接从未被任何断言探测过**：某篇文章的「相关文章」链接写错 slug、标签页链接指向不存在的标签、分页边界……全都不会被发现。
- **更重要的发现**：扩到全站后**当场抓到一个真死链** ——
  ```
  FAIL  链接 /page/7/  (HTTP 404)
  ```
  来源：`src/components/Archive.astro:141`，最后一页（`page === totalPages`）的「下一页」按钮：
  ```astro
  <a class="page-btn" data-dir="next" href={pageUrl(page + 1)} aria-disabled=... tabindex="-1">
  ```
  `aria-disabled` 和 `tabindex=-1` 只挡键盘与 CSS 的点击（`home.css:299` 有 `.page-btn[aria-disabled="true"]`），但 **`href` 照常算成 `page + 1`**，于是 `/page/6/` 里留下一个指向 `/page/7/` 的死链。**URL 是会被爬虫和链接检查器真实访问的**，它不认 `aria-disabled`。
- **措施**：
  1. **修死链**（`Archive.astro:114 / 141`）：禁用态一律指向当前页 ——
     `href={page === totalPages ? pageUrl(page) : pageUrl(page + 1)}`（「上一页」对称处理 `page === 1`）。外观、`aria-disabled`、`tabindex` 全部不变，只是不再产生死链。构建产物里 `page/7/` 引用数从 1 → **0**。
  2. **改断言**（`check.mjs:787-830`）：从「导航首页抓链接」改为「取 `sitemap-0.xml` 的全部页面 URL → 逐页 fetch → 合并去重 → 逐一探测」。并加一条**下限闸门**：
     ```js
     check('全站链接扫描覆盖 sitemap 全部页面',
       pagePaths.length >= 40 && hrefs.length >= 45, ...)
     ```
     这样将来有人把这段改回「只扫首页」，会立刻跌破 45 而报 FAIL。（首页单页仅 29 个，是写进 detail 里的对照数字。）
- **结果/验收**：`PASS  全站链接扫描覆盖 sitemap 全部页面  (54 页 / 60 个站内链接（首页单页仅 29 个）)`；`PASS  全站内部链接可达  (60 个链接)`。
- **故障注入**：把 `/about/` 改成 `/nowhere-404/` → `FAIL  链接 /nowhere-404/  (HTTP 404)` + `FAIL  全站内部链接可达  (61 个链接)`。精确命中。
- **为什么这条最重要**：断言只覆盖首页时，它的标题（「全站」）和它的行为（首页）**不一致** —— 这种「名字说 A、做的是 B」的闸门比没有闸门更危险，因为它给人已经守住的错觉。扩到全站后立刻捞出一条真实死链，正好印证。

## P1-4.4 ✅ 归档页总阅读时长

- **问题**：`src/utils/readingTime.ts` 早就有（中文 400 字/分、英文 200 词/分），文章页也一直在显示「N 分钟阅读」（`PostLayout.astro:115`），但归档页的统计行只有「共 32 篇，约 1.4 万字，跨 1 年、12 个标签」—— 没有总量。
- **措施**（`src/pages/archive.astro`）：
  - 新增 `import { readingTime } from '../utils/readingTime'`；
  - 逐篇 `readingTime(post.body ?? '')` 累加得 `totalMinutes`，再拆成 `hours` / `restMinutes` / `durationText`（<60 分钟给「N 分钟」；整小时给「N 小时」；否则「N 小时 M 分钟」）；
  - 统计行改为「共 32 篇，约 1.4 万字，**读完约 56 分钟**，跨 1 年、12 个标签。」
- **为什么是逐篇累加而不是「总字数 ÷ 400」**：两种算法会给出**不同的数字**（前者每篇向上取整，后者不取）。读者看到「24 篇各 5 分钟、8 篇各 6 分钟」，加起来是 168 分钟，而总字数除 400 可能是 150 分钟 —— 后者是**对不上的假数字**。宁可慢一点也要逐篇累加。
- **措施（断言）**：2 条 ——
  1. 页面显示的分钟数与「从 `search.json` 独立重算的值」相差不超过 **±10%**（口径不完全相同：`search.json` 的 content 是从 Markdown 抽的纯文本，`post.body` 是原始 Markdown，所以留 10% 容差，目的是抓「公式写错/写成固定值」）；
  2. 断言它不是固定值（`!== 1 && !== 100`）。
- **结果/验收**：`PASS  归档页阅读时长与逐篇累计一致（±10%）  (页面=56 独立重算=51)`；`PASS  归档页阅读时长不是固定值  (56)`。
- **故障注入**：把产物里的「读完约 56 分钟」改成「读完约 100 分钟」→ 2 条同时 FAIL（`页面=100 独立重算=51`、`不是固定值 (100)`）。精确命中。
