## 0. 先说结论

这个站点已经过了「缺功能」的阶段。搜索、13 份分频订阅源、JSON Feed、sitemap lastmod、JSON-LD、命令面板、404 出路、主题切换、目录、阅读进度、代码复制都已经做完，而且质量高于同规模个人博客。

本轮真正值得做的不是再堆页面，而是三件事：

1. **把「定时发布」修成真的。** 文档写着未来日期会到点上线，但 `ci.yml` 没有 `schedule`，永远不会自动构建；而且 `date` 按 UTC 零点比较，北京时间实际要等到当天 08:00 才放行。
2. **让 sitemap 只统计已发布文章。** `astro.config.mjs` 的 `readPosts()` 不读 `draft`/`date`，未来文章的日期会把首页、归档、标签、系列的 `lastmod` 提前抬到未来。
3. **补三项低维护的阅读增强。** 打印样式、复制/分享、随机阅读——都不引入框架、不引入第三方脚本、不需要服务端。

内容形态（书架、专题页、系列总览）**本轮不做**。不是代码难，而是内容还没到位；先定触发条件，避免做出空壳页面。

**推荐顺序：批次 A（发布可靠性）→ 批次 B（阅读增强）→ 批次 C 等触发。**

## 1. 站点分析

### 1.1 定位与形态

这是一个个人博客，内容围绕代码、阅读与生活。技术形态是纯静态 Astro：

- `output: 'static'`，构建产物直接部署到 GitHub Pages；
- 内容用 Content Collections（`glob` loader + Zod schema）管理；
- 客户端零框架，只有原生 TS 脚本，依赖 `astro:page-load` / View Transitions 生命周期；
- 没有评论、没有统计脚本、没有推荐算法。

这三条不是「还没做」，而是**明确的设计共识**。本计划的所有候选功能都必须服从它们：能在构建期做完的，不放到运行时；必须用 JS 的，只能是几 KB 的渐进增强；需要后端或第三方托管的，默认不做。

这五条不是风格问题，是**行为、文档、产物三者对不上**。其中前三条会真正影响发布。

| # | 偏差 | 证据 | 影响 |
|---|---|---|---|
| D-1 | 定时发布没有触发点 | `.github/workflows/ci.yml` 只有 `push` / `pull_request` / `workflow_dispatch`，**没有 `schedule`**；`docs/操作文档.md:247-250` 却写「线上会等到那天才出现」 | 未来日期文章不会自动上线，除非恰好有人 push 或手动触发 |

### 1.4 已经做对、不要重做的事

- **搜索**：`/search.json` + 页头 combobox + `/search/` 页 + Cmd/Ctrl+K 命令面板，ARIA 完整；500 字截断后 100 篇估算仍在体积预算内。
- **订阅**：主 RSS、JSON Feed、12 个标签 feed、1 个系列 feed；`/subscribe/` 解释怎么用。
- **SEO**：sitemap 全带 lastmod（T-41 后 60 条）；文章/标签/系列/专题/归档/首页/关于/订阅都有 JSON-LD；`safeJsonLd()` 负责转义。
- **可访问性**：跳转链接、focus-visible、combobox 的 `aria-activedescendant`、无 JS 正文可见、主题三态。
- **性能**：字体 preload、图片 `constrained` + 5 档 srcset、首图优先级；T-27/T-28 已经用实验否掉了字体改动和全局 avif。
- **阅读体验**：目录、阅读进度、代码复制、系列上下文、相关文章、全站上一篇/下一篇、修订记录。
- **内容分发**：RSS 条目覆盖全部文章，最近 20 篇全文，旧文章降级为摘要。

**这些都不需要重做。** 本计划只补真实空缺。

### 1.5 站点给功能设定的边界

站点的设计哲学在 `src/content/posts/small-site.md` 里写得很直白：

> 每加一个部件，就多一份要养的东西。少一个部件，就少一处会坏的地方。

因此：

- 能纯静态构建的，优先；
- 必须客户端 JS 的，限制在几 KB，且无 JS 时有可用退路；
- 需要服务器、数据库、第三方评论、统计脚本的，默认不做；
- 内容型页面必须等内容数据到位再做，不能用空页面占位。

## 3. 批次与顺序

```
批次 A  发布可靠性（必须，约 1.5 天）
  T-34 北京时间语义 + sitemap 过滤
        └──> T-35 每日定时 CI + 文档
                └──> T-36 信号/文案/版本纠偏

批次 B  阅读增强（低风险，约 2 天，可逐项独立）
  T-37 打印样式（纯 CSS）
  T-38 复制链接 / 系统分享（渐进增强）
  T-39 随机阅读（静态 JSON + 页脚脚本）

批次 C  内容形态（触发式，不在本轮）
  T-40 书架 · T-41 专题页 · T-42 系列总览
```

顺序的理由：

1. **T-34 必须在 T-35 之前。** 如果先加 `schedule` 而不修时区，定时任务会在北京时间 00:10 构建，却仍然把当天的文章挡到 08:00——等于把错误自动化。
2. **T-36 放在 T-35 之后。** 定时发布的最终机制（00:10、可能延迟、60 天无活动会停）只有 T-35 拍板后，文档才能一次写准。
3. **批次 B 三项互不依赖。** 但都会碰 `PostLayout.astro` / 页脚 / CSS，建议按 T-37 → T-38 → T-39 串行提交，避免 diff 互相覆盖。
4. **批次 C 不排期。** 触发条件未满足时开工，只会做出没有内容的页面。

| **验证** | ① check fetch `/random.json` 做集合对拍；② 取 `/random.json` 的第一篇文章作为起点，覆写 `Math.random = () => 0`，点击页脚链接，等待导航后断言 `location.pathname !==` 起点且以 `/posts/` 开头（这同时证明当前页过滤生效）；③ 覆写 `window.fetch` 为 reject，点击后断言落到 `/archive/`；④ 故障注入：往 `/random.json` 里塞一个 draft/未来文章 URL → 集合对拍转红；删掉当前页过滤 → 确定性点击测试转红（起点是第一项，`Math.random=0` 会留在原页） |

## 11. 一句话总结

**先把「到点发布」修成真的，再把 sitemap 与文案对齐，最后用打印、分享、随机这三项零维护的小改动把阅读体验收口；书架、专题、系列索引等内容型页面，等数据长出来再做。**

这样做的好处是：每一项都能用现有门禁机械验收，不引入新的运行时，不破坏「静态优先、无评论、无统计、零框架」的定位；而最先修的三项，恰好是**文档已经承诺、但代码还没兑现**的地方。
