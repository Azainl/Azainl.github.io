## 0. 先讲清楚一件事：要不要「变成动态网站」

「静态 → 动态」是这次规划的核心命题，但**它是一个手段，不是目标**。所以第一件事不是选技术栈，而是搞清楚：

> **你到底想要什么，是静态给不了的？**

我把可能的诉求拆成五类，逐条判断：

| 诉求 | 静态能不能做 | 是否需要服务端 | 判断 |
|---|---|---|---|
| **A. 更新内容更省事**（不想每次 `git push`） | ❌ 不能 | **不需要**——可用 Headless CMS / 构建钩子 | 🟢 优先，成本最低 |
| **B. 写作以外的内容形态**（系列、专题、读书笔记卡片） | ✅ 能 | 不需要 | 🟢 优先，纯静态即可 |
| **C. 读者能留下点什么**（评论、点赞、批注） | ❌ 不能 | **需要**（或第三方托管） | 🔴 与现有定位冲突，需决策 |
| **D. 内容能被人找到**（搜索、订阅、分享体验） | ✅ 大部分能 | 不需要 | 🟡 打磨项 |
| **E. 个性化 / 会员 / 付费** | ❌ 不能 | **需要** | ⚪ 暂不进入，除非有明确商业意图 |

**结论**：诉求 A、B、D 占九成以上，而它们**都不需要服务端**。

> ⚠️ **这是本次规划最重要的一条判断**：一个个人博客引入 SSR，收益远小于它带来的运维复杂度（进程要活着、要防冷启动、要备份、要处理时区与会话、CDN 缓存策略全变）。**除非 C 或 E 成为硬需求，否则不要切 `output: 'server'`。**

所以下面的演进路径是：

> **以静态为基线，用 Astro 的「按需渲染」能力做增量**——需要动态时才让那一两个端点动态，其余 99% 的页面永远保持静态。

## 1. Astro 的演进能力边界（技术依据）

这一节是我查证 Astro 官方文档（Context7 `/withastro/docs`）后确认的事实，是整个规划的技术地基。

### 1.1 关键机制：`'static'` 已经内建了混合渲染

**很多人（包括旧文档）以为「静态 → 动态」= 把 `output` 从 `'static'` 改成 `'server'`。这是过时的认知。**

事实（Astro v5 起）：

- `output: 'hybrid'` **已被移除**，其能力**合并进了 `'static'`**；
- 只要**装了 adapter**，任何页面/端点写 `export const prerender = false` **就自动按需服务端渲染**，其余页面照旧静态生成；
- `output: 'server'` 只是「把默认行为反过来」（所有页面默认动态，需要静态的写 `prerender = true`）。

官方原话：

> Start with the default `'static'` mode until you are sure that **most or all** of your pages will be rendered on demand!
> The `'server'` output mode **does not bring any additional functionality**. It only switches the default rendering behavior.

**这意味着**：本站可以**一行配置都不改**，只加一个 adapter + 在特定端点写 `prerender = false`，就获得动态能力。这是「渐进式」的技术基础。

### 1.2 三条演进路线对比

| 路线 | 配置 | 部署产物 | 成本 | 适用 |
|---|---|---|---|---|
| **① 纯静态**（现在） | 无 adapter | 一堆 HTML | 0 | 内容不变、无需交互 |
| **② 静态 + 按需**（推荐） | `adapter: node()`，特定端点 `prerender = false` | 静态 HTML **+** 一个 Node 服务 | 中 | 99% 静态 + 少数动态端点 |
| **③ 全动态** | `output: 'server'` + adapter | 只有 Node 服务 | 高 | 高度动态的应用 |

**本站的路线：长期停在 ②，只有在 C/E 变成硬需求时才考虑 ③。**

### 1.3 路线的代价（必须诚实说明）

走 ② 的代价，不能装作没有：

1. **部署平台要换或要加**。GitHub Pages 是纯静态托管，**跑不了 Node 进程**。动态端点需要：Vercel / Netlify Functions / Cloudflare Workers / 自己的 VPS 之一。
2. **要维护一个「活着的服务」**。进程挂了、冷启动了、内存涨了——这些在纯静态时代完全不存在。
3. **构建产物变成两种**。`dist/` 里既有静态 HTML，又有服务端入口，`deploy.yml` 要重写。
4. **本地开发要区分**。`npm run dev` 会同时跑静态与动态路由，行为与纯静态时不同。

> **所以路线 ② 的第一原则**：**动态端点越少越好**。每加一个动态端点，就多一份运维负担。能用构建期算出来的，绝不放到运行时。

### 1.4 可用的动态能力清单（Astro 内建，无需额外依赖）

| 能力 | 用途 | 本项目可能的用法 |
|---|---|---|
| **API 端点** `src/pages/api/*.ts` | 任意 HTTP 逻辑 | 阅读量统计、搜索代理 |
| **Astro Actions** `src/actions/` | 类型安全的表单/RPC | 留言、订阅 |
| **Sessions** `Astro.session` | 服务端会话 | 登录态、去重计数 |
| **Middleware** `src/middleware.ts` | 请求拦截 | 鉴权、A/B、POST/Redirect/GET |
| **On-demand pages** | 按需渲染页面 | 依赖实时数据的页面 |

会话 API 要点（防会话固定攻击）：`Astro.session?.get('cart')` / `session?.regenerate()`。

## 2. 演进路径总览

四个阶段，**每一个阶段都以「可独立交付、可回滚」为单位**。不要跳阶段。

```
阶段 0  止血          修两个会伤害真实用户的缺陷
         ↓            （不修完不要做别的）
阶段 1  内容平台化    内容结构升级：系列、专题、归档
         ↓            仍是纯静态，收益最大
阶段 2  体验与分发    搜索、订阅、分享、性能
         ↓            仍是纯静态
阶段 3  选择性动态    按需渲染：只有真正需要时才动
         ↓            引入第一个动态端点
阶段 4  能力的边界    评论/会员等需决策项（可选）
```

**为什么阶段 0 必须最先**：A1（JS 失败正文空白）和 A2（JSON-LD 注入）是**正在伤害真实读者**的问题。在一个会让读者看到空白页、会让文章标题被当代码执行的站点上叠加新功能，是没有意义的。

## 3. 阶段 0：止血（1-2 天）

**目标**：消除两个已知的高危缺陷，并建立防回归。

| 任务 | 内容 | 验收 | 优先级 |
|---|---|---|---|
| **P0-1** | 修 A2：JSON-LD 注入（`safeJsonLd`） | `grep safeJsonLd src/` 命中 5 处；含 `</script>` 的探针文章构建后 `STRAY_SCRIPT_COUNT = 0` | 🔴 最高 |
| **P0-2** | 修 A1：JS 失败正文空白 | 阻断 `*/_astro/*.js` 时 `.prose` computed opacity = 1 | 🔴 最高 |
| **P0-3** | 为 P0-1/P0-2 各加一条断言进 `check.mjs` | 断言数从 207 → ≥209；**用故障注入验证断言真的会 FAIL** | 🟠 高 |
| **P0-4** | 修 B1：CI 成为发布门禁 | `deploy.yml` 不再在 check 失败时发布 | 🟡 中 |

**P0-3 的方法论要求**（来自本项目最有价值的经验）：断言必须做**故障注入验证**——先把代码改坏，确认断言报 FAIL，再改回来确认 PASS。一个从来不会失败的自言自语式断言，是纯粹的负担。

**不做的事**：这个阶段不碰样式、不碰内容、不加功能。**只修血**。

## 4. 阶段 1：内容平台化（1-2 周，仍是纯静态）

**目标**：让「写什么」的可能性变多，而不是让「怎么跑」变复杂。

这是**收益最高、风险最低**的阶段——全部是纯静态改造。

### 4.1 P1-1 系列 / 专栏（series）

**现状**：`content.config.ts` 的 schema 没有 `series` 字段。已有 5 篇 Astro 主题的文章天然成系列，却是散落的。

**做什么**：

```typescript
// content.config.ts 新增
series: z.string().optional(),          // 系列标识，如 'astro-notes'
seriesOrder: z.number().optional(),     // 系列内序号
```

```typescript
// src/utils/series.ts 新建
export function getSeriesPosts(posts, series)      // 按 seriesOrder 排
export function getSeriesNeighbors(posts, current) // 系列内的上/下一篇
```

页面侧：文章页加「本系列共 N 篇 · 第 k 篇」条 + 系列导航；新增 `/series/<name>/` 列表页。

**验收**：
- 给 5 篇 Astro 文章加 `series` 后，`/series/astro-notes/` 按 `seriesOrder` 正确排序；
- 文章页显示「第 k / 共 N 篇」，系列内上/下一篇指向正确；
- `npm run typecheck` + `check` 全绿；
- **无 series 字段的文章行为完全不变**（向后兼容）。

**为什么优先**：这是**纯内容建模**，不引入任何运行时；而且它直接提升老文章的复访价值。

### 4.2 P1-2 归档页 `/archive/`

**现状**：无 `archive.astro`；首页既做门面又做归档（`PER_PAGE = 6`）。

**做什么**：新增 `src/pages/archive.astro`——按年月分组的**完整列表** + 总数统计 + 年份锚点。首页回归「门面」定位（保留精选与最近几篇），归档交给归档页。

**验收**：
- `/archive/` 列出全部 32 篇，按年月分组，年份可跳转；
- 首页与归档页的文章集合一致（写断言对拍）；
- 加入 `sitemap` 与 JSON-LD `CollectionPage`；
- 404 页**不出现**归档列表（现有断言 `:341` 已覆盖这点，注意别破坏）。

### 4.3 P1-3 内容形态扩展

| 形态 | 说明 | 成本 |
|---|---|---|
| **读书笔记卡片** | 已有 `books-*` 图与「阅读」标签的底子；结构化「书名/作者/评分/摘录」 | 低 |
| **短想法 / TIL** | 比文章更轻的内容，可入 RSS | 低 |
| **站内专题页** | 手写 `/topics/<topic>/`，人工编排跨标签内容 | 低 |

**建议从「文章修订记录」开始**——`updated` 字段已经在用（sitemap/JSON-LD/RSS 都读了），只是没在文章页显示。**改动最小、立刻可见**。

| 图片全走优化管线 | `public/` 里的图绕过了 Astro 优化，逐步迁到 `src/assets/` | ✅ **盘点后确认已达标**：14 处正文图全部走 `src/assets/images/`；`public/` 下唯一图片是兜底分享图 `og.png`。补了 2 条断言防止将来有人往 `public/` 塞图 |

## 5. 阶段 2：体验与分发（1-2 周，仍是纯静态）

**目标**：让已有的内容**更容易被找到、被读完、被分享**。

### 5.1 P2-1 搜索升级

**现状**：`search.json` 59 KB（含正文全文），随文章数线性增长；100 篇时约 180 KB（见交接文档 §7-C2）。

**做什么**（三选一，按投入排序）：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 索引瘦身** | 只索引标题/描述/标签，正文匹配交给「阅读时高亮」 | 搜索结果精度下降 |
| **B. 分片索引** | 按年份/首字母切多个 json，按需加载 | 实现复杂一点，精度不降 |
| **C. 构建期预生成** | 构建期生成倒排索引，客户端只做查表 | 实现最复杂，效果最好 |

**建议先做 A 的保守版**：正文只保留前 N 字（如 500 字）用于摘要展示，全文匹配降级为可选。**实测体积变化后再决定要不要做 B/C**。

**验收**：`search.json` 体积增长到 100 篇时 < 100 KB；搜索功能不回归（现有断言覆盖）。

### 5.2 P2-2 Cmd+K 命令面板

**做什么**：复用 `search.ts` 的索引与高亮逻辑，加 `Cmd/Ctrl+K` 呼出，支持键盘导航、直接跳转文章/标签/页面。

**注意**：搜索相关的 **ARIA 已经很完整**（`combobox`/`listbox`/`option`/`aria-activedescendant` 全套，关闭时统一复位 `aria-expanded`）。新增面板**必须沿用同一套 ARIA 模型**，不要另起一套。

**验收**：键盘可完整操作（Tab/方向键/Esc）；屏幕阅读器播报正确（复用 `announce()`）；焦点管理无陷阱。

### 5.3 P2-3 RSS 与订阅

**现状**：`/rss.xml` 159 KB，只放最近 30 篇（文档解释了原因）。

**可做的**：
- 分频段订阅（如「只订阅某个标签/系列」）；
- JSON Feed 作为补充格式；
- 订阅页 `/subscribe/` 说明各种订阅方式。

### 5.4 P2-4 性能打磨

**现状实测**：dist 总计 4.19 MB，其中 html 1074 KB / js 31.7 KB / css 30.8 KB。JS 体积很小（31.7 KB），底子很好。

| 项 | 现状 | 动作 |
|---|---|---|
| 字体 | 两个可变字体**每页都 preload**（29 + 51 KB） | 按页面类型条件 preload（衬线只在首页/文章页） |
| 图片 | `layout: constrained` + 只输出 webp | 评估加 avif（文档实测 webp 31.1 KB / avif 20.2 KB） |
| 缓存 | 无 immutable 头（GitHub Pages 限制） | 迁平台才能做 |
| CWV | CLS/INP 实测 0 / 0（已达标） | 保持，加断言防回归 |
| LCP | 首图已 eager + fetchpriority | 保持 |

**注意**：性能优化**必须以测量为准**。项目历史上有一条「首图 lazy 损害 LCP」的假设被 A/B 实测（4 组 × 3 次，含 400kbps 限速）**推翻**（4716ms vs 4712ms，测不出差异），随后降级为「潜在反模式」。**不要凭直觉做性能改动**。

### 5.5 P2-5 SEO 与结构化数据完善

| 项 | 说明 |
|---|---|
| `CollectionPage` 覆盖 | 归档页/系列页/专题页都要带 JSON-LD |
| `BreadcrumbList` | 现有 44 页覆盖，新页面要补齐 |
| `og:type` | 已有 28/28；新页面类型要设对（article/website） |
| 修订时间 | `updated` 已进 sitemap/JSON-LD，确保新页面也带 |

## 6. 阶段 3：选择性动态（按需触发，2-3 天起）

**触发条件**：出现一个**静态真的做不了**的需求，且它**值得**付出 §1.3 列出的运维代价。

**如果触发**，做法如下（**只加一个端点，不全站动态**）：

```bash
npm.cmd i @astrojs/node@11     # 本机最新 11.1.7，本次交接已验证可装
```

```javascript
// astro.config.mjs —— 注意 output 保持默认 'static'，不要改成 'server'
import node from '@astrojs/node';
export default defineConfig({
  adapter: node({ mode: 'standalone' }),
  // output 不动：需要动态的端点自己声明 prerender = false
});
```

```typescript
// src/pages/api/views/[slug].ts —— 唯一改成动态的端点（示意）
export const prerender = false;   // ← 只有这一行让它动态，其余全站仍是静态

export async function GET({ params }: APIContext) {
  const { slug } = params;
  // 读存储（KV / SQLite / 文件），返回计数
  return Response.json({ slug, views: 0 });
}
```

**关键点**：`output` **保持 `'static'`**。只有写了 `prerender = false` 的端点会动态渲染，其余 54 个页面**一个字节都不变**。

**这一步的验收**：
- `npm run build` 后 `dist/` 仍产出全部静态页面；
- 动态端点可通过 `node ./dist/server/entry.mjs` 访问；
- **回滚只需删掉 adapter 那两行**，站点立刻回到纯静态。

**阶段 3 的候选需求**（按「值得程度」排序）：

| 候选 | 需要动态吗 | 值得吗 |
|---|---|---|
| 阅读量统计 | 需要（写入） | ⚠️ 与「无统计脚本」定位冲突，需决策 |
| 站内搜索服务端化 | 需要 | 🟡 索引大到一定程度才值得 |
| 订阅邮件收集 | 需要 | 🟢 但可用第三方表单，不必自建 |
| 内容 API（供外部消费） | 需要 | ⚪ 除非有明确的消费方 |

> **重点**：每加一个动态端点前，先问「有没有更简单的静态替代」。例如订阅收集，用第三方表单就能做，比自己跑 Node 服务简单得多。

## 7. 阶段 4：需要决策的能力（可选）

这两项**都先要决策，再谈实现**。

### 7.1 评论系统——破不破「无评论」原则？

**冲突点**：项目明确「无评论系统、无统计脚本」。引入评论意味着：要么引入第三方（Disqus/Giscus/Utterances），要么自建后端。

| 方案 | 性质 | 代价 |
|---|---|---|
| **Utterances** | 基于 GitHub Issues | 需要读者有 GitHub 账号；引入 `utterances` 脚本 |
| **Giscus** | 基于 GitHub Discussions | 同上，更现代 |
| **自建** | Astro Actions + 存储 | 需要阶段 3 的动态能力 + 防滥用 |
| **不做** | 保持原则 | ✅ 用邮件/社交平台承接反馈 |

**我的建议**：**先不做**。个人博客的互动量通常撑不起维护成本，而「无评论」本身就是一种干净的定位。如果确实想收反馈，`/about/` 里的邮箱（`2013386765@qq.com`）已经够用。

### 7.2 PWA / 离线

**做什么**：`manifest.webmanifest` + 一个简单的 service worker 缓存静态资源与已读文章。

**代价**：service worker 的缓存失效是**出了名的难缠**——发新版本后读者看到旧内容的问题会持续存在。

**我的建议**：只有当你确实想让读者「离线读文章」时才做。否则**不做**。

## 10. 风险清单

| 风险 | 触发条件 | 缓解 |
|---|---|---|
| **动态化过度** | 一个动态端点变成五个 | 每加一个前先问「静态能不能做」 |
| **平台绑定** | 选了 Serverless 平台后难以迁回 | 保持 `output: 'static'` + 只用一个 adapter |
| **断言腐化** | 加了不会失败的断言 | 强制故障注入验证 |
| **文档漂移** | 代码改了文档没改（本项目已发生过） | 把「更新文档」写进任务验收 |
| **技能目录丢失** | `D:\Code\Deepseek` 不是 git 仓库 | 见交接文档 §B2，先做版本控制 |
| **内容增长失控** | 文章过百后构建变慢、索引变大 | 阶段 2 的搜索瘦身 + 定期测量构建时长 |

## 11. 一句话结论

> **不要为了「动态」而动态。**
>
> 本站的九成诉求（更好写、更多形态、更好找）**纯静态就能满足**，而阶段 1、2 全是纯静态改造——**先做完这两阶段，再回头看还需不需要服务端**。
>
> 真要动态时，Astro 的按需渲染让你**只改一行 `prerender = false`**，其余 54 个页面一个字节不变，回滚只需删两行配置。
>
> **但阶段 0 的两个止血任务，必须在任何事情之前完成。**
