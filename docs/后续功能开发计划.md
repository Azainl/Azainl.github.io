## 0. 这份文档解决什么问题

`docs/网站演进规划.md` 已经把「接下来做什么」想清楚了：阶段 2 有 P2-1 到 P2-5 五件事，还列了验收口径。但它是**规划语言**——「搜索瘦身」「按页面类型条件 preload」这类描述读起来明确，一动手就会发现缺三样东西：

1. **缺真实基线**。规划里写的「100 篇时 < 100 KB」「衬线只在首页和文章页」都是估算，本轮实测发现其中**两条前提是错的**（见 §1.3）。照规划直接做，会做出一个测不出收益、或者物理上做不到的改动。
2. **缺可机械判定的验收**。规划说「搜索功能不回归」「CWV 不回归」，但没写用什么判定。本项目的历史规矩是「不做故障注入验证的断言不算数」（交接文档 §6.3），验收必须写成能跑出 PASS/FAIL 的形式。
3. **缺顺序与依赖**。P2-2 在规划的矩阵里依赖 P2-1，但本轮预研发现这个依赖其实不成立（两者加载的是同一个 `search.json`，瘦身只影响加载速度，不影响面板能否实现）。

本文档补齐这三样。**读完本文档 + `docs/开发交接文档.md` 就能直接开工**，不需要再读规划原文。

本文档**不重复**技术栈、目录结构、设计令牌这些已在别处写清楚的内容。

### 1.2 体积账：钱到底花在哪

这是本文档最重要的一张表，因为**性能项的优先级必须由它决定，而不是由直觉决定**。

```
dist 总计 4.20 MB / 102 个文件
├─ 图片  2760.3 KB  66%   ← webp 65 个 2318.1 + png 33 个 442.3（png 全是 OG 卡片）
├─ HTML  1172.7 KB  28%   71 个文件，gzip 后 377.3 KB
├─ 字体    78.5 KB   2%   2 个 woff2，gzip 无收益
├─ 其他     ~79 KB   2%   xml 161.6 KB(gzip 37.1) / json 57.7(gzip 25.9) / js 31.7 / css 33.5
```

**单篇文章页首屏真实传输账**（`posts/borrowed-books/`，DPR 2 桌面）：

| 资源 | 字节 | 可否再压 |
|---|---|---|
| 字体（2 个 woff2） | **78.4 KB** | 只能子集化，gzip 无用 |
| 正文图（取 1152w 档） | 69.2 KB | avif 可到约 45 KB（待实测） |
| 外链 JS | 13.1 KB gzip | 已很小 |
| HTML | 7.0 KB gzip | — |
| 外链 CSS | 6.5 KB gzip | — |

⇒ **首屏瓶颈排序：字体 > 图 > JS > HTML > CSS。**

这张表推翻了两个常见直觉：

- 「图片占 dist 66%，所以优化图片最划算」——**错在口径**。dist 的 66% 是**全部 5 档变体之和**，而单个读者只下载其中 1 档。65 个 webp 来自 13 张源图 × 5 档（640/750/828/1080/1152w），单张源图的 5 档合计约等于 **8 倍**的 1152w 单档。真正落到单个读者头上的是 69.2 KB，不是 2.3 MB。
- 「字体才 78 KB，占 dist 2%，不重要」——**同样错在口径**。字体**每页都要下、且 gzip 压不动**，它是 gzip 后单页最大的单项。

### 1.3 三条必须推翻的旧假设

规划阶段 2 里有三条描述，本轮实测证明不成立。**照原文做会浪费时间，必须先修正认知。**

#### ① 「衬线字体只在首页/文章页用到」—— 不成立

规划 §5.4 的动作写「按页面类型条件 preload（衬线只在首页/文章页）」。实测：

- `src/styles/header.css:45-51`：`.wordmark { font-family: var(--font-serif); … }`
- `.wordmark`（页头的「Az**ain**」字标）**56 个真实页每页都有**。
- 另经逐页核实，`about` / `archive` / `tags` 总览 / `series` / `page/N` / `404` 的首屏 `.page-head h1` 或 masthead 也全部消费衬线。

⇒ **衬线在全部 56 页首屏都会被用到。条件 preload 在物理上做不到。** 这个任务要么放弃，要么换思路（见 T-27：先做 A/B 实验再决策）。

#### ② 「100 篇时 search.json < 100 KB」—— 口径不明，选 raw 就必须截到 240 字

`search.json` 当前 **59049 B raw / 26546 B gzip**，32 条。其中 **content 字段占 49816 B（84.36%）**，其余字段合计 8.8 KB。

更关键的是：`src/pages/search.json.ts:44` 的 `stripMarkdown(...).slice(0, 2000)` **从来没生效过**——32 篇正文 strip 后最短 337 字、中位 549 字、最长 897 字，**0 篇触达 2000 上限**。

阈值矩阵（本轮实测，raw / gzip / 单篇 / 被截篇数 / 100 篇估算）：

| 截断字数 | 当前 raw | 当前 gzip | 单篇 | 被截篇数 | 100 篇 raw | 100 篇 gzip |
|---|---|---|---|---|---|---|
| 2000（现状） | 59049 | 26546 | 1845 | 0 | 180 KB | 81 KB |
| 800 | 58340 | 26241 | 1823 | 4 | 178 | 80 |
| 600 | 54414 | 24585 | 1700 | 13 | 166 | 75 |
| **500** | **49905** | **22629** | 1560 | 19 | 152 | **69** |
| 400 | 43320 | 19791 | 1354 | 27 | 132 | 60 |
| 300 | 35069 | 16242 | 1096 | 32 | 107 | 50 |
| **240** | **29829** | **13866** | 932 | 32 | **91** | 42 |
| 200 | 26348 | 12245 | 823 | 32 | 80 | 37 |
| 150 | 22051 | 10176 | 689 | 32 | 67 | 31 |
| 去 content | 8817 | 3953 | 276 | 32 | 27 | 12 |

⇒ **raw 口径要满足 100 篇 < 100 KB，必须截到 240 字；gzip 口径 500 字就早已达标。** 规划没写口径，这是本轮必须拍板的第一个决策。本文档 §T-21 给的结论是：**选 gzip 口径 + 500 字**。

#### ③ 「P2-2 命令面板依赖 P2-1 搜索瘦身」—— 依赖不成立

规划矩阵把 P2-2 标为「依赖 8（P2-1）」。实际两者读的是**同一个** `/search.json` 与**同一份** `search.ts` 逻辑：瘦身只改变每次拉取的字节数，不改变面板能否实现。把 T-21 和 T-23 串行做只会白等一周。**本文档把两者解耦**（T-23 只依赖 T-22 的 Tab 修复）。

### 1.4 现有门禁的盲区（新功能必须补的断言）

`scripts/check.mjs` 2062 行、191 处 `check(` 调用、运行期累计 246 条。与本计划相关的盲区：

| 盲区 | 现状 | 影响的任务 |
|---|---|---|
| 无 Cmd/Ctrl+K 断言 | 全文件**无** `metaKey`/`ctrlKey` 匹配 | T-22 / T-23 |

### 2.3 为什么是这个顺序

1. **T-21 / T-22 / T-24 先做**，因为它们都只碰一两个文件、改动可逐行复核，且**互不重叠**（分别改 `search.json.ts`、`Header.astro` 的 keydown、`about.astro`+两个 index.astro）。这三个做完站点行为完全一致、体积略降、SEO 补洞，是零风险的净收益。
2. **T-23 排在 T-22 之后**，因为命令面板必然重写 keydown 分支，不先修 Tab 缺陷就会把 bug 一起搬进新逻辑。
3. **T-25 必须是纯重构**，验收是「`dist/rss.xml` 的 sha256 与改前完全一致」。只有这一步真做到零差异，T-26 出问题时才能确定是新增逻辑而非重构引入。
4. **T-27 / T-28 排最后**，因为它们**可能得出「不做」的结论**。规划 §5.4 自己写着「性能优化必须以测量为准……不要凭直觉做性能改动」，而项目历史上已经有一条被 A/B 推翻的性能假设（首图 lazy 案，4 组 × 3 次含 400 kbps 限速，4716 ms vs 4712 ms 测不出差异）。实验类任务的正确产出是**报告 + 决策**，不是代码。

### 3.1 T-21 搜索索引瘦身 + 体积门禁

#### T-21 搜索正文截断改为 500 字，并把 80 篇告警升级为可测门槛 ⚡S

| 项 | 内容 |
|---|---|
| **目标** | 让 `search.json` 的增长有明确上限，且「什么时候该换 Pagefind」这个判断从注释变成可验证的数字 |
| **范围** | `src/pages/search.json.ts`（`:31` 阈值常量、`:44` 的 `slice(0, 2000)`、`:47-53` 的告警分支）；`scripts/check.mjs`（新增体积断言） |
| **不在范围** | **不动** `stripMarkdown()` 的正则链（`:5-19`，它决定了摘要质量）；**不动**客户端 `src/scripts/search.ts` 的打分与排序；**不实现**方案 B 分片索引或方案 C 构建期倒排（见 §3.1 末尾「为什么不现在做 B/C」） |

| **验收** | ① `dist/search.json` raw ≤ **51 KB**、gzip ≤ **24 KB**（当前实测 59049 / 26546，500 字档为 **49905 / 22629**）；② 索引条目数仍为 **32**；③ 长篇正文（如 `powershell-toolbox`）的 content 长度恰好 = 500（被截），短文（如 `hello-world`）长度 < 500（未被截）；④ 站内搜索结果不回归：搜「Astro」仍命中 `astro-*` 系列文章 |
| **验证** | ① `node -e` 读 `dist/search.json` 断言 `Buffer.byteLength` 与 `zlib.gzipSync(...).length` 双阈值；② `JSON.parse` 后断言 `items.length === 32`；③ 断言「被截篇数 === 19」（500 字档实测 19 篇 ≥ 500 字）；④ `npm run check` 中原有的搜索相关断言全部仍 PASS |
| **风险与对策** | 截到 500 字后，正文中位于第 500 字之后的**关键词不再能被搜到**。这是方案 A 的已知代价。对策：`snippet()`（`src/scripts/search.ts:62-72`）只在命中片段附近取「前 40 后 60 字」，截断不影响摘要可读性；且中文博客单篇正文中位 549 字，500 字已覆盖 90% 内容 |
| **依赖** | 无 |
| **技能** | core-web-vitals（字节预算）、performance |

**为什么不现在做方案 B/C**：本轮实测，500 字档在 gzip 口径下 100 篇估算只要 **69 KB**，离 80 篇阈值还有 48 篇的距离。方案 B（分片索引）解决的是「单文件太大」而不是「精度不足」，而现在单文件 22.6 KB gzip 远未到瓶颈；方案 C（构建期倒排）在 100 篇规模下收益 < 20 KB，实现成本却等于重写整个搜索。**先做 A，把数字写进断言，到 80 篇再重新评估**——这正是 `PAGEFIND_THRESHOLD` 这个常量原本的用意。

### 3.2 T-22 修搜索面板的 Tab 键缺陷

#### T-22 给 option 加 `tabindex="-1"`，让 Tab 不再跳进结果列表 ⚡S

| 项 | 内容 |
|---|---|
| **目标** | 修掉一个**现存真 bug**：页头搜索框打开时按 Tab，焦点会直接从输入框跳进第 1 个结果项，而 `aria-activedescendant` 仍指着旧值，读屏软件播报与实际焦点不一致 |
| **范围** | `src/components/Header.astro`（建项循环 `:284-308` 里给 `<a>` 加 `tabindex="-1"`）；`scripts/check.mjs`（新增 Tab 断言） |
| **不在范围** | 不改搜索逻辑；不新增快捷键（那是 T-23）；不改 CSS |
| **根因** | 选项是原生 `<a href>`（`Header.astro:287-292`），天然可聚焦。combobox 模式的正确做法是**选项不进 Tab 序列**——焦点永远留在 input 上，靠 `aria-activedescendant` 虚拟移动。现有实现只做了后半句 |
| **验收** | ① 搜索框打开且输入有结果时，按 Tab **焦点不落在任何 `[role="option"]` 上**；② 面板按 Tab **关闭**（不失焦到隐藏区域）；③ 不 `preventDefault()`——Tab 仍能移到下一个正常元素；④ 鼠标点击选项仍能跳转；⑤ 方向键 + Enter 的现有行为完全不变 |
| **验证** | **必须用 CDP `Input.dispatchKeyEvent`**（`new KeyboardEvent` 是合成事件，不触发浏览器默认行为，测不出 Tab）。该文件至今未用过 `Input` 域，需 `keyDown` + `keyUp` 成对发送。断言：`document.activeElement` 的 `getAttribute('role')` 不得为 `option` |
| **风险与对策** | 给 `<a>` 加 `tabindex="-1"` 会让键盘用户**无法**通过 Tab 到达结果——但这是 combobox 模式的规范行为（WAI-ARIA APG 的 combobox 示例中选项同样不可 Tab 聚焦），键盘用户用方向键 + Enter。断言 ④ 保证鼠标路径不退化 |
| **依赖** | 无（但 T-23 依赖它） |
| **技能** | accessibility（WAI-ARIA combobox 模式） |

## 6. 完成定义（DoD）

每个任务完成的最低标准，与交接文档 §6 一致：

1. `npm run typecheck` → 0 错误；
2. `npm run build` → **57 页**（T-26 新增 /subscribe/ 后由 56 变 57；feed 是端点不是页面，不占页数）；
3. `npm run check` → 全部 PASS，且**断言总数只增不减**（当前 **339**，T-23 收尾时的数字）；
4. 新断言完成**故障注入验证**，记录注入点与 FAIL 数量；
5. `git diff` 逐行复核通过；
6. 文档同步：本文件对应任务的复选框勾选 + `docs/开发交接文档.md` 相关段落更新。

**验证命令（Windows 环境特别注意）**：

```bash
# 必须用 npm.cmd（Windows 下裸 npm 会 EINVAL）
npm.cmd run typecheck

# check 必须对 preview 跑，不能对文件系统跑
# 终端 A：
node node_modules/astro/bin/astro.mjs preview --port 4321 --host 127.0.0.1
# 终端 B：
npm.cmd run check
```

> `astro` 的入口是 `node_modules/astro/bin/astro.mjs`，**不是** `astro.js`（后者不存在，会报 `Cannot find module`）。
> preview 必须常驻：`check` 会 `fetch` `127.0.0.1:4321`，进程一退就 `ECONNREFUSED`。
