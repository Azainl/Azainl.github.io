## 二、S-1（高）：JSON-LD 注入 —— ✅ 已修复（任务三）

> **修复**：`src/utils/jsonld.ts` 新增 `safeJsonLd(data)`，把 `<` `>` `&` `U+2028` `U+2029` 转成 JSON 层转义序列；四处调用点全部替换。回归断言（源码契约 5 处 + 构建产物逐块 `JSON.parse` 可解析 + 文章页 ld+json 块数 ===1）已加入 `check.mjs`。

### 2.1 漏洞位置

四处页面用 `set:html` 把 JSON 直接写进 `<script>`：

| 文件 | 行 |
|---|---|
| [src/layouts/PostLayout.astro](src/layouts/PostLayout.astro) | 84 |
| [src/pages/index.astro](src/pages/index.astro) | 69 |
| [src/pages/page/[page].astro](src/pages/page/[page].astro) | 54 |
| [src/pages/tags/[tag].astro](src/pages/tags/[tag].astro) | 59 |

写法是：

```astro
<script type="application/ld+json" is:inline set:html={JSON.stringify(jsonLd)} slot="ld" />
```

**问题**：`JSON.stringify` 不转义 `<` 和 `>`。HTML 解析器不认 JSON 语法，它只找字面的 `</script`。于是标题里的 `</script>` 会**提前闭合脚本标签**，其后内容被当作普通 HTML 解析 —— 注入的 `<script>` 或 `<img onerror>` 会真的执行。

### 2.2 实测证据

构造一篇文章，标题与摘要各带一个探针：

```yaml
title: "PROBE</script><script>window.__hit.push('TITLE')</script>"
description: "PROBE</script><script>window.__hit.push('DESC')</script>"
```

构建后产物里，JSON-LD 段确实被截断：

```
<script type="application/ld+json">{"@context":"https://schema.org","@graph":[{"@type":"BlogPosting","headline":"PROBE</script><script>window.__hit...
                                                     ^^^^^^^^^ 脚本在此提前闭合
```

用无头 Chrome 打开构建后的页面，读 `window.__hit`：

```
A-asis           hit=["TITLE","DESC","TITLE"]     ← 三次执行
M-meta-only      hit=["TITLE","DESC","TITLE"]     ← 只转义 meta 无效
J-ldjson-only    hit=[]                           ← 只转义 JSON-LD 即完全消除
B-both           hit=[]                           ← 全部转义
```

**归因结论**：把这份 HTML 拆成四个变体（A 原样 / M 仅转义 meta 的 `content` / J 仅转义 JSON-LD / B 都转义），逐个在浏览器里跑。**只有动 JSON-LD 的那两个变体停止执行**。这排除了「是 meta 属性导致的」这一直觉误判 —— meta 里虽然也出现了未转义的 `</script>`，但它在属性值里不构成执行路径，真正能执行的是 JSON-LD。

### 2.3 真实触发路径（不需要攻击者）

这才是严重度之所以为「高」的原因：**这不是理论边界，正常写作就会踩到**。

实测一篇标题为「关于 `</script>` 标签的一个坑」的文章（一篇讲前端知识的正常投稿）：

```
LDJSON_PARSEABLE = ["PARSE_FAIL"]     ← 结构化数据被解析器抛弃
STRAY_SCRIPT_COUNT = 10               ← 多出一个游离的 script 节点
BODY_LEAKED_TEXT = true               ← 标题后半段泄漏成可见正文
```

后果分三层，随标题内容而升级：

1. **功能性后果（必然发生）**：JSON-LD 不再是合法 JSON，搜索引擎**完全读不到**文章的结构化数据 —— 而 T-02/T-03/T-18 三个任务专门做这件事，等于被静默抵消。
2. **内容损坏（必然发生）**：`</script>` 之后的内容脱离头部，泄漏为页面正文。
3. **脚本执行（取决于内容）**：若标题含可执行片段，则直接执行。

> 本项目是个人博客、作者写自己的文章，**不构成「被他人攻击」的真实威胁**。但第 1、2 层后果**不需要任何人恶意**就会发生 —— 一篇文章讲 `</script>` 的坑，就足以让它自己的结构化数据失效并弄乱排版。这属于「必须修的缺陷」，而非「可选项」。

### 2.4 修复方案

加一个转义函数，四处在输出前统一过一遍：

```ts
// src/utils/jsonld.ts
/**
 * 把 JSON-LD 安全地放进 <script> 里。
 * 必须转义 < > &（以及 U+2028/2029），否则正文里的 </script> 会提前闭合脚本，
 * 导致结构化数据失效、内容泄漏，甚至执行注入的脚本。
 */
export function safeJsonLd(data: unknown): string {
  return JSON.stringify(data)
    .replace(/</g, '\\u003c')
    .replace(/>/g, '\\u003e')
    .replace(/&/g, '\\u0026')
    .replace(/\u2028/g, '\\u2028')
    .replace(/\u2029/g, '\\u2029');
}
```

调用处改为 `set:html={safeJsonLd(jsonLd)}`。

**注意**：用 `\u003c` 这种 JSON 转义而不是 HTML 实体（`&lt;`）是刻意的 —— `<script>` 是**原始文本元素**，HTML 实体在其中**不会被解码**，写 `&lt;` 反而会让 JSON 里的字符串变成字面量 `&lt;`，污染结构化数据。

### 2.5 建议同时加的回归断言

本次四个变体的实验说明：**只有 JSON-LD 这一层是执行路径**。应在 `check.mjs` 中固化：

```
PASS  结构化数据可被 JSON.parse（标题含 </script> 时）
PASS  页面无多出的游离 script 节点
```

判据取「产物里 `<script type="application/ld+json">` 段内不出现字面 `</script>`」，比比对字符串更稳。

## 四、S-3（中）：缺少内容安全策略

线上抓取实测响应头（`https://azainl.github.io/`）：

```
HTTP/1.1 200
Strict-Transport-Security: max-age=31556952     ✅ 有
Access-Control-Allow-Origin: *                  ⚠️ GitHub Pages 默认
Cache-Control: max-age=600
Content-Type: text/html; charset=utf-8
（无 Content-Security-Policy / X-Content-Type-Options / Referrer-Policy / Permissions-Policy）
```

**HTTPS 与 HSTS 是好的**（Pages 强制 HTTPS，HSTS 有效期约一年）。缺的是 CSP。

GitHub Pages **无法自定义响应头**，所以传统 CSP 头这条路走不通。可用替代方案：

1. `<meta http-equiv="Content-Security-Policy">` —— 功能弱于响应头（不支持 `frame-ancestors`、`report-uri`），但对 `script-src` 有效，足以作为 S-1 的纵深防御。
2. 迁到 Cloudflare Pages / Netlify（仓库里已有 [netlify.toml](blog/netlify.toml) 与 [vercel.json](blog/vercel.json) 配置），即可用 `_headers` 文件发真正的响应头。

**难点要如实说**：本站有 4 处内联脚本（主题 FOUC 兜底、`astro:before-swap`、`ensurePageMatchesUrl` 等）加 Astro 的 ClientRouter。启用 CSP 需要给它们加 nonce 或 hash，而**静态预渲染产物的 nonce 是构建期固定的** —— 等于把 nonce 变成常量，安全收益归零。所以实际可行的是 hash 方案，需要把内联脚本逐个抽成外部文件，与「首屏同步执行避免 FOUC」的诉求直接冲突。

**建议**：先修 S-1（根因），把 CSP 作为独立任务评估，不要为了打勾而加一个 `unsafe-inline` 的假 CSP。

## 七、S-9（低）：缓存策略未利用内容哈希

实测带 hash 的资源与 HTML 返回同样的 `Cache-Control: max-age=600`：

```
/_astro/ClientRouter...C0MNin66.js   →  Cache-Control: max-age=600
/_astro/BaseLayout...DQRH0vj8.css    →  Cache-Control: max-age=600
/`                                   →  Cache-Control: max-age=600
```

文件名里的 hash 就是为「内容变了才变、可永久缓存」设计的，但 `max-age=600` 让回访者每 10 分钟就重新校验一次。**这是 GitHub Pages 的硬限制**（不能自定义头），只有迁到支持 `_headers` 的平台（Netlify/Vercel/Cloudflare Pages）才能把 hashed 资源设成 `max-age=31536000, immutable`、HTML 设成 `no-cache`。

**代价与收益要量化后再决定**：收益是回访更快，代价是换平台。建议记为「若将来迁移时顺手做」，不单独为它迁移。
