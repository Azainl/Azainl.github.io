### 1.3 本轮新发现的问题（下面各任务的依据）

**① 可访问性零覆盖（确定）**

`check.mjs` 里 `aria` 出现 95 次、`Tab/键盘` 76 次、`aria-live` 13 次——但分散在
**DOM 选择器与交互脚本**里，`check()` 调用中没有一条以「语义是否正确」为断言对象。
对比度（`contrast`）为 **0**。

具体风险：`pages.css` 的 `mark` 曾实测浅色 4.21:1 不达 AA，修复后是
**浅色 5.37:1 / 深色 4.98:1**，但这个结论**只存在于 CSS 注释里**，没有任何断言守着。
换句话说：现在有人把 `--mark-bg` 改回半透明，CI 依然全绿。

**② 外链从不检查（确定）**

`check.mjs` 有「全站内部链接可达」断言，但 `href="http` 出现 **0 次**——外链（含
Wikimedia / Unsplash 的署名链接）从没被验证过。文章越写越多，外链只会更多。

**③ 图片 alt 只有 1 处检查（确定）**

43 篇文章、21 张图，`alt` 相关的断言只有 1 条。空 alt 对屏幕阅读器等于「一张无用图」，
对 SEO 也是浪费。

**④ Pagefind 阈值遥远（定量）**

`search.json` 单篇 1578 B。距 `PAGEFIND_THRESHOLD = 80` 还差 **37 篇**，
按近四个月平均（约 10 篇/月）算约 **4 个月**；按 11 月产量（5 篇）算要 **7 个月以上**。
→ **现在换 Pagefind 是过早优化**，但要留刻度。

**⑤ 检查脚本自身臃肿（定性）**

`check.mjs` 已 4905 行，单文件。改一处要滚很久，且失败定位靠 grep。这是**下一批任务会加剧**的债。

## 4. 任务书

### 4.1 T-44 可访问性断言：把「已修好」变成「修好了且有守卫」🟠M

| 项 | 内容 |
|---|---|
| **目标** | 至少覆盖三件会真实伤害用户、且历史上**真的坏过**的事：搜索高亮对比度、正文图 alt、焦点可见性 |
| **为什么现在做** | `mark` 的 5.37:1 / 4.98:1 只写在注释里；改回半透明 CI 全绿。这是最典型的「修复会静默回退」 |
| **范围** | 只加断言到 `check.mjs`，**不改任何产品代码**（除非断言抓出真问题） |
| **具体断言（建议 6 条）** | ① 浅色 `mark` 对比度 ≥ 4.5；② 深色 `mark` 对比度 ≥ 4.5；③ 文章页所有 `img` 的 `alt` 非空且非文件名；④ `img` 必须有 `width`/`height`（防 CLS）；⑤ Tab 到页头链接时 `outline` 不为 none；⑥ 搜索面板打开后 `aria-live` 区域存在 |
| **对比度怎么量** | 在页面里取 `getComputedStyle` 的 `color`/`background-color`，用 WCAG 相对亮度公式算，**不要写死期望值**（改了设计令牌就得重算） |
| **验收** | 6 条全绿；**每条都做故障注入**（如把 `--mark-bg` 改成半透明 → ①② 必须转红） |
| **不做** | 不引入 axe-core / pa11y 等新依赖（体积与调试成本不划算）；不做全站 WCAG 扫描 |

### 4.2 T-45 断链检查扩到外链 ⚡S

| 项 | 内容 |
|---|---|
| **目标** | 站内链接已守；把**外链**也纳入，至少做到「HEAD 请求不通时报警」 |
| **具体做法** | 从 `dist` 收集 `href="http...]` 的外链 → 去重 → 并发 HEAD（超时 5 s）→ 4xx/5xx 记失败。写进 `check.mjs` 的既有断链段落 |
| **必须处理的两件事** | ① **网络不稳定会让 CI 假红** → 失败时重试 1 次，仍失败才判红，且把状态码写进消息；② 有些站点拒绝 HEAD → 回落 GET |
| **验收** | 全站外链通（当前约 30～40 条）；故意写一条 `https://httpstat.us/404` 的假链 → 断言转红 |
| **不做** | 不做外链归档 / 快照；不检查锚点是否有效（成本高收益低） |

### 4.3 T-46 图片与内容的机器校验 ⚡S

| 项 | 内容 |
|---|---|
| **目标** | 把「靠人记」的几件事变成断言：OG 图存在性、文章 `description` 长度、标签必须在 `tags.ts` 里登记 |
| **为什么** | 刚写的五篇文章全靠我手动核对 alt/图注/日期；这些是**可机械化**的 |
| **具体断言** | ① 每篇已发布文章的 `description` 在 20～120 字（太长被截断，太短没信息量）；② 所有文章用到的 tag 都在 `tags.ts` 里（否则 URL 变百分号编码）；③ 每篇正文若有图，正文里必须有对应的斜体署名行 |
| **验收** | 全绿；故障注入：把某篇 description 改到 200 字 → 转红 |
| **不做** | 不校验中文语法 / 文风 |

### 4.4 T-47 依赖升级到 Dependabot 提议的版本 🟠M

| 项 | 内容 |
|---|---|
| **目标** | 合并两个挂着很久的 Dependabot PR：astro → 7.3.8、source-serif-4 → 5.3.1 |
| **为什么现在做** | 当前「以 lockfile 为准」意味着本地与 CI 都停在 7.3.5，而生态已往前走了；早升少痛 |
| **做法** | `npm i astro@7.3.8 @fontsource-variable/source-serif-4@5.3.1`（走 lockfile 更新，不手工改）→ 全量门禁 → 观察构建产物差异 |
| **风险** | Astro 小版本可能改 markdown 管线（我们用了 `satteri` 的 hastPlugin）；**必须逐条看 build 日志与 dist 差异** |
| **验收** | typecheck/test:unit/build/check 全绿；dist 页数仍 69；图片管线仍输出 webp |
| **回滚** | 单个 commit，`git revert` 即可 |

### 4.5 T-48 check.mjs 按断言域拆分为多个文件 ⚡S

| 项 | 内容 |
|---|---|
| **目标** | 把 4905 行拆成 `scripts/checks/` 下若干模块（导航 / 主题 / 内容 / feed / a11y / 断链），主文件只负责编排 |
| **为什么** | 下一批要加 6～10 条断言，塞进单文件只会更难维护 |
| **硬约束** | **行为零变化**：拆分前后断言总数必须都是 503（或拆分时的当前值），且逐条名称不变。拆分本身**单独一个 commit**，不与新断言混提 |
| **做法** | 每个模块导出 `async function(ctx)`；`ctx` 提供 `check / runPage / evaluate / BASE` 等既有工具 |
| **验收** | 拆分前后各跑一次全量 check，**逐行 diff 输出**确认只有执行顺序可能不同、结果集一致 |
| **不做** | 不顺手改任何断言的逻辑（那是另一个 commit 的事） |

### 4.6 T-49 Pagefind 迁移的刻度（⏸ 触发式）

| 项 | 内容 |
|---|---|
| **触发条件** | 已发布文章 ≥ **60 篇**（不是 80）时开始评估；≥ 80 篇必须迁移 |
| **为什么提前到 60** | 单篇 1578 B，80 篇 = 126 KB raw / 约 57 KB gzip。用户首次聚焦搜索就要下载这些，已经偏重 |
| **现在做什么** | 只把刻度写进文档 + 在 `search.json.ts` 的 `console.warn` 阈值旁加注释说明 60 篇先评估 |
| **届时评估项** | ① Pagefind 能否索引中文（需实测分词）；② 与现有 `Ctrl+K` 命令面板的兼容成本；③ 构建时间增加多少 |
| **不做** | 现在不预研、不装包 |

## 6. 验收定义（DoD）

每个任务收尾必须同时满足：

1. `npm run typecheck` 0 错误
2. `npm run test:unit` 全过
3. `npm run build` 页数符合预期（当前 69，新增页面时说明增量）
4. `npm run check` 全绿，且**新增断言做过故障注入**（转红 → 恢复 → 再绿）
5. 文档同步：若改动了断言数 / 页数 / 依赖版本，更新 `开发交接文档.md` 与本文进度表
